# Plugin registration — plugins ship as code

A plugin version becomes routable when core has it **REGISTERED**. There are two ways that happens,
and one place people act on plugins: the environment's **ops console**.

## 1. Automatically, on every deploy (normal case)

`deploy.sh` → `scripts/register-plugins.py` runs after a deploy is healthy and live:

1. For each plugin in the release (`backend/plugins/*/plugin-manifest.json`) it builds the exact
   manifest for this environment: committed manifest + the running plugin's public client key
   (`plugin_manifests.py`, the same code `observe.py` uses for drift).
2. It posts them to core `POST /internal/release/plugins` (internal credential **and** the release
   credential `FSP_RELEASE_CREDENTIAL`, which only core and the deploy hold — never the gateway/BFF).
3. Core (`PluginLifecycleService.reconcileRelease`):
   * same manifest already registered → nothing;
   * new version → REGISTERED, older version DEACTIVATED, machine client provisioned (owner: platform root);
   * same version, new content (e.g. rotated key) → updated in place; a person's pending PLUGIN_REGISTER for it is withdrawn;
   * plugin suspended **by a person** → left suspended (`held_suspended`); only a PLUGIN_RESUME lifts it;
   * registered plugin no longer shipped → SUSPENDED (reason RELEASE), data kept.

**Who are the four eyes?** (AGENTS.md §2.1 exception.) The pull request author and its approving
reviewers, plus — production — the GitHub environment's deploy approvers. `_deploy.yml` writes them
to `provenance.json`; core stores it on the row (`plugin_types.provenance`, `registered_via=RELEASE`,
`registered_by` NULL — no FSP maker, never a machine one) and in the audit/outbox records.

| | staging | production |
|---|---|---|
| `FSP_PLUGIN_AUTOREGISTER` | 1 | 1 |
| `FSP_PLUGIN_AUTOREG_SECOND_PERSON` | 0 — the merged PR is enough | 1 — someone other than the author must have approved the PR or the deploy, else nothing is registered |
| `FSP_RELEASE_CREDENTIAL` | generated by the deploy | **provision it** in the production `.env` to turn this on |

The run summary on GitHub and `deploy-history` show what was registered. The gateway reloads routes within 60 s.

## 2. By people, in the ops console (four-eyes)

Each environment has its own Grafana at **`https://<env host>/ops/`** (staging:
`https://fsp.stage.afriqpay.com/ops/`). FAPI 2.0: Grafana never talks to the IdP and holds no
token — nginx asks the environment's BFF (`/bff/ops/auth`) who is signed in and passes only that
name to Grafana's auth proxy. Platform staff only; everyone is a Grafana *Viewer*.

Dashboard **FSP releases & plugins › Plugins**:

* **Register** a shipped version by hand (maker, needs `plugin.register`).
* **Suspend** — out of service: the gateway answers `503 PLUGIN_SUSPENDED`, the IdP refuses the plugin's client, data stays.
* **Resume** — back in service.
* **Approve / Reject** pending requests — a *different* person (needs `plugin.manage`).

Every button is the person's own call through the BFF → gateway → core, so core decides
permissions and maker ≠ checker. Buttons ask for a second click to confirm; nothing uses browser dialogs.

## Operations

* First time / after changing nginx: `bash ~/fsp-monitor/stack/scripts/monitor-bootstrap.sh`
  (adds `include /etc/nginx/snippets/fsp-ops-<env>.conf` to the environment's vhost and turns the
  old `fsp-monitor.stage` Grafana into a redirect; that host keeps `/manifests` behind basic auth).
* Production console: set `GRAFANA_PRODUCTION_ENABLED=1` in `deploy/monitoring/monitor.params`
  (and raise the monitor slice by 512 MiB), then re-run the bootstrap.
* Break-glass Grafana admin: ssh tunnel to `127.0.0.1:29300/ops/` with the admin password from `~/fsp-monitor/.env`.
* Isolation note: each console shows only its environment's dashboards, but Prometheus/Loki are
  shared datasources — a soft boundary. A hard one needs a label-enforcing proxy per environment.
